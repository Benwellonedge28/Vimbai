# Catalogue

The one place the estate is described: every service the gateway routes, the domain that owns it, where that domain's code
lives, and whether its figures already come from Rust.

Generated by `cargo run -p xtask -- catalog` from two sources of truth that already existed:

1. `gateway/go/config/services.json` - the routes the gateway actually serves, in its order.
2. `catalog/ownership.json` - which domain owns each service, and where that domain's code lands.

Nothing here is typed by hand, and `rust/xtask/tests/catalog_is_current.rs` fails if these files drift from the generator.
That matters more than it sounds: this repository has already had three different counts of the same services, and a
catalogue that can disagree with the router is worse than none.

## Files

```
catalog/services/catalog.yaml      every service, in gateway order
catalog/services/<domain>.yaml     the same services grouped by owner
```

Each entry carries the port, the gateway path, whether authentication is required, how many endpoints the service answers
itself, whether it still owns records, and whether its figures come from the Rust engine. The `target` field is where the
domain lands in the Rust workspace.

## What this is not

It is not an API contract. The contracts under `contracts/` are the versioned, agreed shape of what a caller may ask for.

It is not a deployment plan either. `engine` says where the arithmetic runs, not what should be deployed separately.
