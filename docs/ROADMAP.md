# Vimbai roadmap

The plan this repository is worked to. It is ordered: each phase assumes the one before it, and a phase is only
finished when its exit criteria are met with evidence committed to the repository. Nothing here is scheduled by date,
because the work is sequential rather than calendar-driven. Progress is recorded in the status table at the end, which
is updated in the same commit that lands the work.

Scope: bring the repository in line with the target architecture in `docs/Vimbai_Design_Document_V1.5.md` and the
proposed repository tree, one verified step at a time.

Out of scope by decision:

- *Vimbai Pay.* Not built in this roadmap at all. The `domains/payments` crate stays as it is (POS till support) and no
  provider adapters, settlement, or reconciliation work happens. See ADR-005.
- *Developer platform.* Deferred, not built. See ADR-006, which records the trigger conditions that would reopen it.

## 2. Rules that apply to every phase

These are standing instructions. A phase that breaks one is not finished.

1. *Safe Rust only.* `#![forbid(unsafe_code)]` in every library and application crate. No `unsafe`, no exceptions.
2. *One source of truth.* Each calculator, route and shared helper is registered once. Duplicate implementations are
   deleted, not left to drift.
3. *No duplicate registrations.* `test_no_http_address_is_registered_twice` must keep passing. One handler answering two
   addresses is deliberate only for a retired service's published path.
4. *`./scripts/preflight.sh` before every push.* It is cargo-only: fmt, clippy with `-D warnings`, the whole workspace,
   and it builds `vimbai-local` first so the five offline tests run instead of skipping.
5. *Prove before deleting.* Nothing is retired until its replacement answers the same addresses with the same figures,
   pinned by a test.
6. *Ledger entries are immutable.* Corrections are reversing entries. ledger-core is the only authority for posting
   integrity, balance, immutability and the hash chain; no second ledger is built inside a domain.
7. *Exact money.* No floats in financial arithmetic. `Money` is `BigDecimal`; JSON carries it as a string.
8. *Base64 for binary.* Any binary or encrypted blob crossing JSON is base64 encoded.
9. *Gates get stricter, never looser.* A tolerated exception must be deleted, never added to, except with a written
   reason in the phase commit.
10. *Descriptions match reality.* Documentation states what exists and what is planned, separately and explicitly.

## 3. Sequence

Order matters because of these dependencies:

```
P0 documents and hygiene
 └── P1 dependency rules + gate
      └── P2 organisations and tenancy  ──┬── P6 contracts
           ├── P3 financial integrity      │    └── P7 Flutter feature-first
           ├── P4 worker                   │
           └── P5 domain documentation ────┘
                └── P8 data layer (needs your database decision)
                     └── P9 sync-server
                          └── P10 infrastructure
                               └── P11 close-out
```

P2 gates P6 and P7 because a contract or a client data layer written before the organisation boundary exists has to be
rewritten after it. P8 needs a decision from you (see section 5) before it can start.

### P0. Freeze the boundaries, tidy the root

Purpose: settle the arguments in writing before any structure moves, and remove the last legacy surface.

Tasks

- P0.3 `ADR-003-modular-platform.md` — one crate per business domain; the deliberate divergences table from section 1.
- P0.4 `ADR-004-api-versioning.md` — versioning, error envelope, pagination, idempotency keys, Book scope header.
- P0.5 `ADR-005-vimbai-pay-deferred.md` — not built; what would have to be true to build it.
- P0.6 `ADR-006-developer-platform-deferred.md` — deferral with trigger conditions.
- P0.7 `ADR-007-data-storage.md` — recorded only after the decision in section 5, not before.
- P0.8 `ADR-008-directory-naming.md` — refuses cosmetic crate renames; records the reason.

- P0.10 Fold `MIGRATION-MAP`, `MIGRATION-MANIFEST`, `RUST-MIGRATION-BACKLOG`, `SERVICE-CONSOLIDATION`,

- Every ADR merged except ADR-007, which waits on section 5.
- `git ls-files` contains no `web-frontend/` path and no `.db` file.
- No two documents in `docs/` describe the same thing differently.

### P1. Make the boundaries enforceable

Purpose: a rule with no gate behind it is a comment.

Tasks

- P1.1 `docs/architecture/system-boundaries.md`: what each layer owns, in one page.
- P1.2 `docs/architecture/dependency-rules.md`, phrased as checkable statements: `calculations` may not import
  `domains`; only `kernel/ledger-core` may post; `gateway/go` carries no financial logic; a domain reaches another
  domain only through its published surface, never its internals.
- P1.3 New gate in `rust/xtask/src/wiring.rs` (or a sibling): parse each crate's `Cargo.toml` and fail on a dependency
  the rules forbid. Assert the scan found crates, so an empty read cannot pass.

Exit criteria

- The gate fails when a forbidden dependency is added (prove it by adding one temporarily in a test fixture, not in the
  real tree).
- `cargo run -p xtask -- wiring` reports nothing outstanding and `cargo test -p xtask` is green.

### P2. Organisations and tenancy

Purpose: the boundary every later phase keys on, and the one thing currently missing from the code.

Tasks

- P2.1 `docs/domains/organisations.md`: the hierarchy organisation → book → legal entity → records; what owns what;
  which records are org-scoped, book-scoped, or both.
- P2.2 `rust/crates/domains/organisations` (or an extension of `platform/tenancy`, decided in P2.1): the
  `Organisation` entity, its commands and queries, and its relationship to Books.
- P2.3 Make the hierarchy real in the store: an organisation owns Books, a Book belongs to one organisation, records
  inherit both scopes. No record may be written without a resolvable owner.
- P2.4 Enforcement in one place: a single membership check used by the api-server and by `local-runtime`, replacing any
  second copy.
- P2.5 Tests: a user in two organisations sees only the active one's Books; a Book cannot be read across an organisation
  boundary (403, not an empty list); creating the first organisation for a user works with no prior context.

Exit criteria

- The five tests in P2.5 pass over HTTP.
- No code path writes a record with an unresolved organisation.
- `grep` finds no second implementation of the membership check.

### P3. Financial integrity, proven

Purpose: the invariants ledger-core owns must be provable without reading the crates that use them.

Tasks

- P3.1 Move the invariants into a dedicated suite `rust/tests/financial-integrity/` (or
  `rust/crates/kernel/ledger-core/tests/` if a workspace-level test crate proves awkward): an entry must balance, a
  posted entry is immutable, a reversal nets to zero against its original, the hash chain breaks if a posted line is
  altered, and no float ever enters the comparison path.
- P3.2 Property tests: random entry sets, of random sizes, with amounts of arbitrary precision, always balance after
  double entry is applied.
- P3.3 Parity fixtures under `rust/tests/fixtures/parity/`: the figures the retired Python services produced, kept as
  evidence the Rust engine reproduces them.
- P3.4 `docs/compliance/financial-integrity.md`: what is guaranteed, and by which test.

Exit criteria

- The suite fails if `#[forbid(unsafe_code)]` is removed from ledger-core, if a reversal is not a reversal, or if the
  hash chain is bypassed.
- Every claim in P3.4 names a test file and function.

### P4. A worker that actually runs the automation

Purpose: `domains/automation` schedules and executes, and nothing runs it.

Tasks

- P4.1 `rust/apps/worker`: consumes scheduled automations from the same store the engine uses, with the same
  `#![forbid(unsafe_code)]` attribute.
- P4.2 Idempotent execution: a run that crashes mid-flight does not double-post. A completed run is never repeated.
- P4.3 Scheduled notifications land in the inbox the notifications crate already exposes.
- P4.4 Tests: a rule due now fires once; a rule due later does not fire; a crash between claim and completion leaves the
  run claimable exactly once.

Exit criteria

- `cargo test -p vimbai_worker` green, including the crash case.
- The worker starts from the same store file the local runtime writes.

### P5. Domain documentation, as built

Purpose: 26 domain crates exist and are undocumented outside their code.

Tasks

- P5.1 `docs/domains/accounting.md`, `finance.md`, `banking.md`, `budgeting.md`, `costing.md`, `taxation.md`,
  `treasury.md`, `reporting.md`, `assets.md`, `equity.md`, `partnerships.md`, `audit.md`, `compliance.md`,
  `workflow.md`, `automation.md`, `analytics.md`. One to three pages each: what it owns, its published addresses, its
  commands and queries, its tests, and what it deliberately does not own.
- P5.2 Each document names the crate path and the addresses it serves, verified against
  `cargo run -p xtask -- gateway --addresses`.
- P5.3 `docs/domains/payments.md` is written only to state that POS support exists and Vimbai Pay does not.

Exit criteria

- Every routed service maps to exactly one document, and the mapping is checkable against `catalog/services/catalog.yaml`.

### P6. Contracts, versioned and tested

Purpose: an API that changes without a test is not an API.

Tasks

- P6.1 `contracts/openapi/v1/` with one specification per domain that has a public surface, generated from or checked
  against the actual routes.
- P6.2 `contracts/compatibility/api-compatibility-policy.md`, `event-compatibility-policy.md`,
  `deprecation-policy.md`.
- P6.3 A gate: every published address appears in a contract, and every contract path is answered. Both directions,
  because a contract nobody serves and a route nobody documented are the same defect.
- P6.4 The conventions from ADR-004 implemented rather than described: one error envelope, cursor pagination, idempotency
  keys on writes, `X-Book-Id` as the scope header.

Exit criteria

- Adding a route without a contract fails a test. Removing a route a contract names fails a test.
- The six existing flat YAMLs are replaced, not duplicated.

### P7. Flutter, feature first

Purpose: 58 dart files in five layer folders will not scale to 25 features.

Tasks

- P7.1 Prove the pattern on one feature: `apps/flutter/lib/features/payments` (the POS screens, not Vimbai Pay) with
  `presentation/ application/ data/ models/` and its tests.
- P7.2 Then migrate the remaining features in this order: authentication, organisations, books, accounting, reporting,
  and the rest. Behaviour-preserving moves, no redesigns in the same commit.
- P7.3 `lib/core/` for api client, auth session, local database, offline manager, errors and logging; `lib/app/` for
  router, bootstrap, config and theme.
- P7.4 `test/` and `integration_test/` populated as features move, so coverage follows rather than chases.
- P7.5 Platform folders (android, ios, web, windows, linux, macos) generated once the structure is stable.

Exit criteria

- No dart file remains in `lib/models`, `lib/pages`, `lib/services`, `lib/widgets` or `lib/local_db`.
- The app builds and the existing widget tests pass, unmodified except for import paths.

### P8. Data layer

Blocked on the decision in section 5. Not started before it.

Tasks

- P8.1 `docs/architecture/data-ownership.md`: which component is authoritative for each record, and the transaction
  boundary around accounting and payment records.
- P8.2 `data/schemas/` per domain; `data/migrations/registry.yaml` with ordered versions and a rollback path.
- P8.3 `data/seeds/` for currencies, jurisdictions and accounting standards, loaded idempotently.

- P8.5 `data/backup/` policies and a verified restore, exercised by a test rather than described in prose.

Exit criteria

- A migration applies, rolls back, and re-applies cleanly against a copy of a real store file.

### P9. Offline and sync

Purpose: the app claims offline-first; `platform/offline-sync` exists and no server side does.

Tasks

- P9.1 `rust/apps/sync-server` implementing the contract the offline-sync crate already defines.
- P9.2 Conflict resolution: last-writer-wins only where provably safe; accounting records refuse conflicting writes
  rather than silently choosing.
- P9.3 Tests: a device that was offline syncs once, not twice, on reconnect; a conflicting edit is refused with a
  reason; a partially uploaded batch resumes rather than restarting.

Exit criteria

- The three scenarios in P9.3 pass against a real `vimbai-local` process, not a mock.

### P11. Close-out

Purpose: leave a repository where every deviation is recorded once, and no gate is being lenient.

Tasks

- P11.1 Empty the exception baselines: `infrastructure/kubernetes/stripped-path-collisions.json`, the known method
  gaps, and any pinned tolerance list. Each entry is either fixed or written up as a permanent, reasoned exception.
- P11.2 Rewrite `docs/architecture/overview.md` from the finished tree rather than the proposed one.
- P11.3 `docs/migration/migration-status.md` set to complete, with the three permanent divergences stated.
- P11.4 ADR-008 reviewed: are any of the naming refusals now cheap enough to reverse?
- P11.5 Final full `./scripts/preflight.sh`, final catalogue regeneration, `CHANGELOG.md` entry, `VERSION` bump.

Exit criteria

- Every gate reports zero tolerated exceptions, or the exception is an ADR with a reason.
- A new contributor can go from clone to a running local runtime using only `docs/README.md`.

## 4. Definition of done, per phase

Borrowed from the target architecture's completion gates. A phase is finished when:

1. The behaviour is covered by a test that fails without the change.
2. `./scripts/preflight.sh` is clean and the work is pushed.
3. No duplicate implementation of the same rule was left behind.
4. Any published address affected is answered at the same path, with the same figures.
5. `docs/` describes it accurately, in the right place, with no contradiction elsewhere.
6. Nothing was tolerated that could have been fixed, and anything tolerated says why.

## 5. Decisions needed from you

1. *Database direction (blocks P8).* Keep Neo4j as the server store, move accounting and payment records to a
   transactional relational store, or keep both with a split by ownership? My recommendation is to keep the property
   store for relationships and add a relational store only for records needing multi-statement transactions, decided
   after the data-ownership map exists. It is your call and the roadmap does not assume an answer.
2. *Deployment target (shapes P10).* Kubernetes primary with Compose for development, or the reverse? Today both exist
   and neither is authoritative.
3. *Untracking `web-frontend/` (P0.12).* Confirmed reversible from history, but it is your data.
