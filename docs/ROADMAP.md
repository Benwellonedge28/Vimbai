# Vimbai roadmap

The plan this repository is worked to. It is ordered: each phase assumes the one before it, and a phase is only
finished when its exit criteria are met with evidence committed to the repository. Nothing here is scheduled by date,
because the work is sequential rather than calendar-driven. Progress is recorded in the status table at the end, which
is updated in the same commit that lands the work.

Scope: bring the repository in line with the target architecture in `docs/Vimbai_Design_Document_V1.5.md` and the
proposed repository tree, one verified step at a time.

Out of scope by decision:

- *Vimbai Pay.* Not built in this roadmap at all. The `domains/payments` crate stays as it is (POS till support) and no
  provider adapters, settlement, or reconciliation work happens. See ADR-005.
- *Developer platform.* Deferred, not built. See ADR-006, which records the trigger conditions that would reopen it.

## 2. Rules that apply to every phase

These are standing instructions. A phase that breaks one is not finished.

1. *Safe Rust only.* `#![forbid(unsafe_code)]` in every library and application crate. No `unsafe`, no exceptions.
2. *One source of truth.* Each calculator, route and shared helper is registered once. Duplicate implementations are
   deleted, not left to drift.
3. *No duplicate registrations.* `test_no_http_address_is_registered_twice` must keep passing. One handler answering two
   addresses is deliberate only for a retired service's published path.
4. *`./scripts/preflight.sh` before every push.* It is cargo-only: fmt, clippy with `-D warnings`, the whole workspace,
   and it builds `vimbai-local` first so the five offline tests run instead of skipping.
5. *Prove before deleting.* Nothing is retired until its replacement answers the same addresses with the same figures,
   pinned by a test.
6. *Ledger entries are immutable.* Corrections are reversing entries. ledger-core is the only authority for posting
   integrity, balance, immutability and the hash chain; no second ledger is built inside a domain.
7. *Exact money.* No floats in financial arithmetic. `Money` is `BigDecimal`; JSON carries it as a string.
8. *Base64 for binary.* Any binary or encrypted blob crossing JSON is base64 encoded.
9. *Gates get stricter, never looser.* A tolerated exception must be deleted, never added to, except with a written
   reason in the phase commit.
10. *Descriptions match reality.* Documentation states what exists and what is planned, separately and explicitly.

## 3. Sequence

Order matters because of these dependencies:

```
P0 documents and hygiene
 └── P1 dependency rules + gate
      └── P2 organisations and tenancy  ──┬── P6 contracts
           ├── P3 financial integrity      │    └── P7 Flutter feature-first
           ├── P4 worker                   │
           └── P5 domain documentation ────┘
                └── P8 data layer (decided: ADR-007)
                     └── P9 sync-server
                          └── P10 infrastructure
                               └── P11 close-out
```

P2 gates P6 and P7 because a contract or a client data layer written before the organisation boundary exists has to be
rewritten after it. P8 was the one phase waiting on you; it stopped waiting when ADR-007 was accepted.

### P1. Make the boundaries enforceable

Purpose: a rule with no gate behind it is a comment.

Tasks

- P1.1 `docs/architecture/system-boundaries.md`: what each layer owns, in one page.
- P1.2 `docs/architecture/dependency-rules.md`, phrased as checkable statements: `calculations` may not import

- P1.3 New gate in `rust/xtask/src/wiring.rs` (or a sibling): parse each crate's `Cargo.toml` and fail on a dependency

Exit criteria

- The gate fails when a forbidden dependency is added (prove it by adding one temporarily in a test fixture, not in the
  real tree).
- `cargo run -p xtask -- wiring` reports nothing outstanding and `cargo test -p xtask` is green.

### P2. Organisations and tenancy

Purpose: the boundary every later phase keys on, and the one thing currently missing from the code.

Tasks

- P2.1 `docs/domains/organisations.md`: the hierarchy organisation → book → legal entity → records; what owns what;
  which records are org-scoped, book-scoped, or both.
- P2.2 `rust/crates/domains/organisations` (or an extension of `platform/tenancy`, decided in P2.1): the
  `Organisation` entity, its commands and queries, and its relationship to Books.
- P2.3 Make the hierarchy real in the store: an organisation owns Books, a Book belongs to one organisation, records
  inherit both scopes. No record may be written without a resolvable owner.
- P2.4 Enforcement in one place: a single membership check used by the api-server and by `local-runtime`, replacing any
  second copy.
- P2.5 Tests: a user in two organisations sees only the active one's Books; a Book cannot be read across an organisation
  boundary (403, not an empty list); creating the first organisation for a user works with no prior context.

Exit criteria

- The five tests in P2.5 pass over HTTP.
- No code path writes a record with an unresolved organisation.
- `grep` finds no second implementation of the membership check.

### P3. Financial integrity, proven

Purpose: the invariants ledger-core owns must be provable without reading the crates that use them.

Tasks

- P3.1 Move the invariants into a dedicated suite `rust/tests/financial-integrity/` (or
  `rust/crates/kernel/ledger-core/tests/` if a workspace-level test crate proves awkward): an entry must balance, a

- P3.2 Property tests: random entry sets, of random sizes, with amounts of arbitrary precision, always balance after

- P3.3 Parity fixtures under `rust/tests/fixtures/parity/`: the figures the retired Python services produced, kept as

- P3.4 `docs/compliance/financial-integrity.md`: what is guaranteed, and by which test.

Exit criteria

- The suite fails if `#[forbid(unsafe_code)]` is removed from ledger-core, if a reversal is not a reversal, or if the
  hash chain is bypassed.
- Every claim in P3.4 names a test file and function.

### P8. Data layer

**Decided in ADR-007**, and narrowed on 2026-11-25: Postgres is the system of record for a deployment and SQLite on a
device, Neo4j is frozen rather than extended, several stores in one deployment is deferred, and every provider Vimbai
offers has to pass one conformance suite (`tests/every_store_keeps_the_same_rules.rs`).

Tasks, in the order they were done:

- P8.1 **Done.** A record and its edge doors: `all_edges` and `create_edge` on the store trait, so a relationship is
  something the store is asked for rather than something a caller infers.
- P8.2 **Done.** `vimbai_store::dump` takes every record of every record kind, plus every edge, and restores them exactly as
  they were. Edges travel as data on purpose: a restore that re-derived relationships from fields would rebuild yesterday's
  data using today's rules, and a migration that quietly rewrites history is worse than one that fails.
- P8.3 **Done.** `vimbai-store-move <from> <to> [dump file]` with `file:<path>` and `neo4j` stores, comparing the arrival
  against the source and exiting 1 on anything it cannot prove. Nothing is removed from the source.
- P8.4 **Done.** A gate over the dump catalogue: `KINDS` is checked against the constants the crate declares, so a record
  kind cannot be added and silently never move.
- P8.5 **Done.** `Graph` now carries seventeen semantic doors - create a record in a Book, create one with the children it
  owns, read, list, replace fields, delete, look up by a token, walk an account's postings, and the platform-record
  equivalents - and `Records` and `PlatformRecords` both use them. A caller asks the store to do something instead of
  handing it a query. The Cypher those doors carry is a transition, not the design: it is the statement the old callers
  wrote, moved into the trait so the behaviour did not change while the shape did. A backend that refuses `run` outright
  and answers only the doors serves every caller, which is what the Postgres implementation has to be, and that is a test
  rather than a claim. A gate over the crate's own source fails if a caller goes back to writing statements.
- P8.9 **Done.** `vimbai-store-move` is a cutover verb with a receipt: `--plan` counts what would move by kind and says
  whether the destination is empty, a destination that already holds records is refused in words rather than allowed to mix
  two books (`--into-occupied` to mean it), `--receipt` writes what happened, and `--rehearse` marks a receipt so it cannot
  be read as a cutover. Four tests over a file store: the plan's counts, the occupied-destination refusal, a faithful
  receipt naming both stores, and a rehearsal that says so on its first line.
- P8.10 **Done.** `VIMBAI_SCHEMA_MODE=apply|verify` with one decision point, `migrations::decide`, used by both the device
  and the deployment store: apply brings a store up (the default), verify refuses a store that is behind, naming its
  version, the expected one and the way out, which is what a managed database whose credentials cannot create tables needs.
  Four tests pin it, including that a store written by a newer build is refused in either mode.
- P8.10 **Done.** Neo4j is read from and never written to. A deployment with no `VIMBAI_POSTGRES_URL` refuses to start and
  names the setting it wants instead of falling back to the frozen store, and the move tool refuses Neo4j as a
  destination while still lifting books out of one.
- P8.11 **Done.** The raw statement door takes a `Statement` only the store crate can mint, so the contract every service
  sees is operations and nothing else: no handler, service crate or script can send Cypher, because none of them can make
  the thing the door asks for. Stores implemented outside the crate still read what they are asked through
  `Statement::cypher` and `Statement::params`. A content gate fails if any `fn run` takes a bare Cypher string again or
  the token's fields become public. ADR-007 carries the reasoning in its 2026-11-25 amendment.
- P8.9 **Done.** A store states what it can do - its name, whether it keeps relationships, whether two writes can stand
  or fall together - and a store that says nothing is taken at the minimum. The move refuses a destination that cannot
  hold what the source carries before it writes anything, so detection advises and never decides. The conformance suite
  checks every store can hold a relationship, which is what a Book that can be dumped faithfully needs.
- P8.8 **Done.** One conformance suite, every store. `rust/crates/adapters/database/tests/conformance/mod.rs` holds the
  rules a provider must keep, and `tests/every_store_keeps_the_same_rules.rs` runs them against the memory graph, the file
  store, SQLite, and Postgres wherever a server is available. It pins, naming no dialect: a record reads back as written,
  another Book sees nothing and cannot reach a record by id, another kind holds nothing, an update changes only what it
  named, a figure survives to the last digit, a listing holds every record of the Book once, a page from a place holds
  exactly the rows after it in id order, a delete removes the record and a second delete is refused, and an edge written is
  an edge reported. Portability was a claim made by one trait; it is now a fact a provider has to pass. ADR-007 carries the
  amendment: Postgres and SQLite are the two targets, Neo4j is frozen rather than extended, and several stores in one
  deployment is deferred with the seam kept ready for it.
- P8.7 **Done.** SQLite is the device store, answering the semantic doors natively instead of through statements: a real
  schema with foreign keys and indexes, WAL so a reader never waits on a writer, and a migration that applies in numbered
  steps and rolls each one back, so a laptop that is upgraded can also be put back. A whole-file rewrite per change is what
  used to stand between a crash and a Book, and it is gone: an entry and its lines arrive in one transaction, a posting
  that is refused leaves no edge and no half entry, and two hundred writers on one store lose nothing. Shared rows -
  memberships, sync batches, organisation links - gained their own doors, because a Book written through a statement would
  still have failed on the device; they are implemented natively too, and the source gate now reads their file as well.
  The on-device runtime opens `store.db`, and a machine that already had `store.json` is carried into it once on first
  boot, with the old file renamed rather than deleted: an upgrade that ate its own source is the one migration nobody can
  check afterwards. Eleven device-store tests plus the five end-to-end ones, which now run against SQLite.
- P8.6 **Done.** Postgres, and tested against a real server rather than a fake: eleven tests run against Postgres 15,
  covering Book isolation, an entry and its lines in one transaction, a refused posting that leaves no edge and no half
  entry, an amount carried to thirty-nine digits exactly, shared rows, twenty-four concurrent writers losing nothing, four
  Books writing at once, and a Book carried from SQLite into Postgres and compared on arrival. Two things had to be right
  that a fake would never have shown. First, the client is synchronous and drives its own runtime, so a query issued
  inside the engine's async runtime panicked with "cannot start a runtime from within a runtime" - every operation now runs
  on a thread of its own, which also stops a slow query stalling other requests. Second, the record column is `jsonb`, so a
  parameter sent as text was refused; the record now travels as a value. The engine reads `VIMBAI_POSTGRES_URL` and prefers
  it to Neo4j, which stays reachable for anyone still running it, and preflight now starts a throwaway cluster when the
  server binaries are installed so these tests run instead of skipping.
  The engine itself is covered too, not only the store: `apps/api-server/tests/postgres_engine_http.rs` gives the router a
  Postgres store and writes, reads back, keeps two Books apart, and finds the record still there after the store is
  reopened, plus which store the engine picks when both Postgres and Neo4j are configured (Postgres, per ADR-007; the
  Neo4j address it is offered points at nothing, so choosing it would fail rather than quietly succeed).

Exit criteria

- *Met.* A Book written in one store arrives identical in another: every record, every edge, an amount carried to
  thirty-nine digits, and a book-scoped read that still works on the far side. Nine tests, and a swap between two
  different implementations rather than two instances of the same one.
- *Met.* A dump that is truncated or edited is refused rather than half loaded.
- Not yet met: a migration applied, rolled back and re-applied against a copy of a real store file. That needs the
  relational store, so it belongs with P8.6.

## 4. Definition of done, per phase

Borrowed from the target architecture's completion gates. A phase is finished when:

1. The behaviour is covered by a test that fails without the change.
2. `./scripts/preflight.sh` is clean and the work is pushed.
3. No duplicate implementation of the same rule was left behind.
4. Any published address affected is answered at the same path, with the same figures.
5. `docs/` describes it accurately, in the right place, with no contradiction elsewhere.
6. Nothing was tolerated that could have been fixed, and anything tolerated says why.
