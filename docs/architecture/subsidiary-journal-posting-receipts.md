# Work package 47 — Commit subsidiary journal records with their postings

Proposed design. Source reviewed at [2c0642c](https://github.com/Benwellonedge28/Vimbai/commit/2c0642cd994674e4d455e93d524031eb6477e9a1).

## Where the write can split

In `rust/crates/domains/accounting/src/subsidiary_journals.rs`, `create_sale` gets a journal ID from its posting helper before calling `remember` for the sales row. `create_purchase`, `create_receipt`, `create_disbursement`, `create_sales_return`, `create_purchases_return` and `create_vendor_bill` also post before saving their source rows. A write failure between those operations leaves general-ledger activity without the source record the user expects to see. The HTTP idempotency middleware in `rust/apps/api-server/src/idempotency.rs` claims keys before dispatch and records the responses after the handler returns. The journal needs its own durable evidence at the point of commit.

## Posting and replay contract

Use the scoped transaction in [package 22](opening-balance-receipts.md). Within it, reserve the key `(owner scope, Book, authenticated actor, journal kind, operation ID)`, prepare and create the ledger entry through `ledger_book::create_entry`, and save the source row and receipt before commit. Each successful receipt stores the source row ID, full journal ID, canonical request digest and digest version. Distinguish all seven journal kinds. A human-readable invoice, voucher or reference number belongs in the evidence. Different operations may use the same display reference.

For an explicit HTTP `Idempotency-Key`, the configured accounting handlers pass the caller-owned key into the command context after scope resolution. Register these seven writes and their aliases with the existing idempotency layer as transaction-backed writes. Its generic path-and-body claim must yield to their durable receipt, so a crashed generic claim cannot block a valid retry and the two aliases share one operation identity. Old stored HTTP claims remain replayable under their original actor, path and raw-body fingerprint. An older in-progress claim with no completed response requires scoped review before re-execution. Preserve the published paths, successful response shapes and keyless requests. An unkeyed request receives a server-generated operation ID for that execution, with atomicity but without a cross-request identity. Pass the same operation ID through any internal retry. Replaying a client key on another alias for the same journal kind must find the same receipt. Bind the digest to the accepted source fields, including effective date, counterparty, references, exact amounts, document currency and rate inputs, and explicit tax and account selections. Normalize decimal representations and object key order. Keep meaningful line order and exclude generated timestamps and IDs. For foreign receipts and disbursements capture the foreign units, linked document and exact carrying amount in that digest. Pass the same transaction handle into `fx_settlement::settle_foreign` for those paths, and require its full journal ID before saving the source row. Look up a receipt after authorization and before reading mutable chart or tax defaults. Return the original source response on a match, including its journal ID.

Keep `post`, `post_lines`, `post_taxed` and `post_taxed_lines` on the shared posting path. The persisted journal keeps the converted Book amounts, the source keeps the existing document currency evidence, and per-tax rows created by the taxed path participate in the same commit. Resolve posting purposes through the mechanism in ADR-018. Use the existing closed-period rule and the kernel's balance and hash checks. Every store read or lock used in making the write decision must use the transaction handle.

## Callers and failure behavior

`rust/apps/api-server/src/accounting_book.rs` carries the key and keeps the paired list and detail handlers readable. `apps/flutter/lib/features/invoicing/data/sale_posting.dart` and `apps/flutter/lib/features/payables/data/purchase_posting.dart` send and retain one key per submitted form across timeouts. A user-confirmed revision starts a fresh submission. Return 409 for reuse with different inputs and show “This submission already recorded a different journal. Open that record before trying again.” A closed period uses the existing period refusal. A transaction failure shows “The journal and its source record could not be saved. Retry this submission.” A committed retry after the period closes remains a read of the stored result.

## Older Books

Existing source and journal IDs stay readable. Recover a missing link only when an authorized audit finds a unique same-Book journal with matching source module, date, reference, accounts, currency evidence and exact lines. A legacy record has no recoverable operation key unless existing evidence identifies it. Send ambiguous cases to a scoped review with the candidate IDs. Keep posted entries and their hashes intact during repair.

Put the shared accounting transaction cases here so they can exercise both store adapters without adding an accounting dependency to the database crate. Assert the previous hash head, tax records and source count remain intact after restart.
- Add `subsidiary_retry_across_aliases_reuses_journal_after_close` to the accounting HTTP tests. Race matching calls, then replay through the other alias after closing the period. Also simulate a lost HTTP response immediately after commit and replay it. Change the date on the same key and assert a conflict. Use the same display reference in another Book and assert independence.
- Add `posting_retry_keeps_form_submission_key` to each of the two Flutter posting adapters' tests. Simulate a lost response and verify that a confirmed edit gets a distinct key.
- Add `legacy_subsidiary_link_repair_refuses_two_matching_journals` beside the domain tests. Verify the repair leaves both existing journals readable.

Accept the package when a successful journal can be traced from its source after restart, and failure at any write boundary leaves both absent.
